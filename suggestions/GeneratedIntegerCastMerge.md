# Generated integer ranges across architectures

WinXPSkin's progress segments exposed three upstream limitations while generating the same XML for x86 and x64.

An explicit `Int32` cast around native-integer range endpoints passed Workflow semantic compilation but produced structurally different C++: the redundant cast disappeared on x86 and remained on x64. [Workflow/Source/Cpp/WfMergeCpp.cpp](https://github.com/vczh-libraries/Workflow/blob/master/Source/Cpp/WfMergeCpp.cpp) accepts integer type/literal substitutions, but cannot merge that additional cast. The first failure was reported at row 21846, columns 171/201, in the generated progress subscription. Consistent redundant-cast emission or expression normalization before merging would support this case.

A fixed-width range with conversions from `double` generated and merged successfully, then failed C++ compilation on x64. [Vlpp/Source/Collections/OperationEnumerable.h](https://github.com/vczh-libraries/Vlpp/blob/master/Source/Collections/OperationEnumerable.h) declares `RangeEnumerator<T>::Index()` as returning `T`; its `IEnumerator<T>` base requires native `vint`. Instantiating a range of `vint32_t` on x64 therefore produces C2555. The proposed upstream correction is to return `vint` from `Index()`, with x86/x64 tests using fixed-width and native-width range values.

The generic boxed item-parameter shorthand also fails: `<ref.Parameter Class="system::Object" .../>` becomes `system::Object^`, which semantic validation rejects because the boxed value is not a class or interface. [GacUI/Source/Compiler/WorkflowCodegen/GuiInstanceLoader_WorkflowCollectReferences.cpp](https://github.com/vczh-libraries/GacUI/blob/master/Source/Compiler/WorkflowCodegen/GuiInstanceLoader_WorkflowCollectReferences.cpp) should special-case the boxed object in `Workflow_GetSuggestedParameterType` and cover that constructor parameter in an item-template regression.

The final local workaround in `Source/WinXPSkin/UI/Template_Scroll.xml` uses a native-integer range and an `ItemTemplate-eval` factory that ignores its ordinal argument and constructs a parameterless `ProgressChunkTemplate`. The factory's only operation is template construction; chunk count, six-pixel width, two-pixel spacing, gradients, and layout remain declarative XML. This avoids fixed-width range instantiation, architecture-dependent casts, and the boxed constructor-parameter shorthand. No generated or upstream code is edited manually. Regression coverage should include empty, partial, and complete progress values.
